## Decisions

- **The main feed is a recent window: the last 14 days, and at most 200 posts, whichever is fewer (2026-11-26).** Jenna's numbers; they're `FeedWindow.days` and `FeedWindow.maxPosts` in `Library.swift`, and nowhere else.
  - **What was wrong:** the feed was every saved post of every blyg. It had no end, and each rebuild (and the build as the app opens, which is on the main actor) read through every post's HTML for its text and first picture: more work every day.
  - **Measured by the date the feed already sorts by:** a post's claimed `updated`, capped at when this phone first saw that version. So a blyg followed today puts only its last 14 days in the feed, not its archive.
  - **Less work, not only fewer rows:** posts are picked and sorted by date first, and a row is built only for a post that will be shown. One first seen before the cut-off is passed over without parsing its date. Every saved post is still looked at once per rebuild, which is a date comparison each. A test counts the rows built.
  - **Nothing is deleted.** The library and its file keep every post.
  - **Each blyg's page lists all its saved posts,** under a new "All posts" row, built off the main actor when opened. That page had no list of posts before: the feed was the only place to read them, so without the list a post older than the window couldn't be opened at all. A link to a saved post is looked up in the library, not the feed, so one too old for the feed still opens in the app. The counts on Your blygs are of every saved post, as before.
  - **The feed ends with a line:** "You're up to date" and how far back it goes (the last 14 days, or the newest 200 posts and the date of the oldest), then where the older posts are. With posts saved but none recent it says "No posts in the last 14 days", and the feed still shows: otherwise New post and pull to refresh would vanish after a quiet fortnight.
  - **The window moves when the feed is rebuilt,** not as time passes with the app open: as the app opens, and on any refresh that tries a blyg, whether or not it answers.
  - **Unfollowing the blyg that filled the feed rebuilds it,** so the other blygs' posts, which were below the 200th row, move up. Any other unfollow just takes its rows out, as before.
  - **On fixtures** (UI tests, screenshots) the window is measured from the fixture blyg's own date, or from `-feedNow`: its posts are dated November 2026.
  - *Beat:* every saved post in one list (what it was); deleting old posts to bound the work (loses what's saved for reading offline).
- **A blyg your Studio follows that can't be reached gets three tries, one per launch (2026-11-26).** Jenna's rule. Before, it was remembered as seen at the first failure and never tried again, and the first import did the same (listed as known after Codex's third review, below).
  - **Pending, not seen:** when following it fails because no blyg answers at its address (a network error, a timeout, a 404, a page that isn't a blyg), it goes on the connected blyg's `pendingFollows` with a count of tries, and stays out of `studioFollows`.
  - **Tried again once per launch,** in the launch refresh (`refreshAtLaunch`) and nowhere else: not on pull to refresh, not on coming back from the background. So an address that's gone is asked three times at most, never on a loop.
  - **One try per address per launch, whichever list wants it.** Two connected Studios that both list a dead address share one request and one count: three tries between them, not three each. A blyg the first import couldn't reach isn't tried again by a launch refresh still running in that same launch. The count for the launch is kept apart from the lists, so it outlives a list that's switched off or disconnected meanwhile.
  - **A Studio's addresses are spelled the way the app spells one typed in** (a trailing slash, no query), so the same address matches across lists, on the pending list and when it's followed by hand. A list remembered by an earlier build is compared the same way.
  - **Three tries in all** (`PendingFollow.maxAttempts`), the first included. Then it's remembered as seen and left alone, as before. One that answers on any try is followed like any other and leaves the list.
  - **It leaves the list untried** when keeping in step is switched off, the blyg is disconnected or unfollowed, or the Studio stops listing it. Followed by hand, under the address the Studio lists or the one that address redirects to, it leaves the list and is remembered as seen, so unfollowing it later doesn't bring it back. Unfollowed while a Studio's list is still asking after it, it stays unfollowed when the answer comes.
  - **The first import uses the same rule,** and its result line says Blyglet will try again. It now remembers each blyg as it's dealt with, like any later refresh, so closing the app part-way leaves the rest for the next refresh (it used to save the whole list first, and the rest were skipped for good). Those followed already are remembered together at the start; each of the others the moment it's in the library, in the same save and before its posts are fetched. Disconnecting or unfollowing part-way stops it, and a refresh leaves the list alone while the import has it.
  - **Unfollows are noted for as long as any Studio's list is being worked through,** from before the list is asked for: a blyg unfollowed then isn't followed again, whether its answer was on its way or its turn was still to come. A blyg followed by hand while a list was asking after it is dealt with, even if the list's own request then fails.
  - **A blyg a list asks for that's followed already isn't refreshed by that follow.** There's nothing new to fetch; and if it's itself a Studio keeping in step, with the same address on its own list, that refresh would wait for the follow that started it.
  - **Saved with the library,** as an optional field of the saved blyg: a file from build 10 loads, and the file's version stays 1 (build 10 reading a newer file would ignore the list, and drop it on its next save).
  - **Inside the launch refresh:** a retry is one more blyg in that refresh. It resolves off the main actor, shows through the same paced rebuild, and is saved by the same one save at the end.
  - **What it costs:** the launch refresh isn't over ("updating…" in the masthead, and its save) until each pending blyg has answered or failed, one at a time: for a dead address, usually three or four requests (the resolver allows six), each given up after 20 s without data and 60 s at the outside. Other blygs' posts show meanwhile, and leaving the app saves at once. Tries are counted in that end-of-refresh save, so an app killed in the middle of a launch refresh can forget a try.
  - **A launch can pass without a retry, and nothing makes up for it:** when the Studio's own blyg can't be refreshed (offline, its server down), when its list can't be read (an expired token), or when that blyg is already being refreshed. Nothing is tried and nothing counted; the next launch tries. That's the rule as set: the launch refresh, and nowhere else.
  - **A blyg the Studio drops and lists again starts afresh,** with three tries, even one given up on before: what's remembered as seen has always been only what the Studio still lists. The Studio's list is read up to 2,000 entries, as before; one beyond that counts as dropped.
  - *Beat:* never retrying (a blyg that was down for an hour dropped off the list for good); retrying on every refresh (hammers a dead address).
- **Refreshing does its heavy work off the main actor, and once per refresh (2026-11-26).** A tester's build 9 hung, suspected while refreshing; there was no crash log, so this comes from reading the code, and the hang was never reproduced.
  - **What was wrong:** the app's types are on the main actor by default. A refresh of every blyg decoded each blyg's manifest and index there, then rescanned every saved post to rebuild the timeline, then encoded the whole library, read and decoded the old file, copied the backup and wrote: all once per blyg, so the cost grew with the number of blygs times the size of the library.
  - **Now:** the syncer and the resolver are `@concurrent`. A refresh of several blygs (launch, pull to refresh, coming back to the app) saves once, at its end, and rebuilds the timeline at a pace while blygs arrive: no sooner than half a second after the last rebuild finished, taking along every blyg that has arrived by then, and once more at the end. The rebuild and the write run off the main actor, one at a time; a change that arrives meanwhile gets one more pass, so the newest library always has the last word.
  - **Nothing is lost by waiting to save:** when the app leaves the screen, what a refresh was holding back is written at once and each later blyg as it arrives; every write holds background time; a failed write is tried again.
  - **Posts appear blyg by blyg.** The first version rebuilt once, at the end of the refresh, as Jenna's brief asked; new posts then waited for the slowest blyg, up to 20 s for one that can't be reached. With the rebuild off the main actor that wait bought nothing, and Jenna changed the brief the same day. *Beat:* one rebuild at the end; a rebuild per blyg, which rescans the library once per blyg.
  - **Also:** which blygs have a token is kept in memory, because views asked the Keychain on every redraw; unfollowing drops a blyg's rows without a rescan; keeping in step with a Studio remembers each new blyg as it's tried and stops if switched off part-way.
  - **Still on the main actor, left for later (Jenna, 2026-11-26):** the library is read and its timeline built once as the app opens (so it opens with posts in place); Your blygs counts each blyg's posts on every redraw; and one Keychain read per refresh of a connected blyg that keeps in step. (The first import of a Studio's follows used to save the whole list before adding any, so closing the app part-way skipped the rest: fixed with the retry rule, above.)
  - **Known and not changed, from Codex's third review:** a refresh asked for while that blyg is already being refreshed is dropped, so a post published at that moment can be missing until the next refresh; switching keeping in step off and on while the Studio's list is being fetched can save the older list. (The third, a blyg a Studio follows that can't be reached and was never tried again, now has its retry rule: see the decision above.)
  - **From Codex's fourth review, of the third's fixes:** a write that fails gives the refreshes it had covered their save back, so a refresh still running saves at its end; a blyg followed by hand while a Studio's list is being worked through is remembered as dealt with; unfollowing a blyg with no posts showing tells no view and copies no row. The tests that time the pace still run on real time, with wide margins: a clock the tests could set would make them exact, at the cost of one more thing passed into the model.
  - *Beat:* an actor for the store (callers' saves could still arrive out of order); saving per blyg off the main actor (still one full rewrite per blyg).
- **Codex's review of the feed window and the retry rule (2026-11-26): what wasn't changed, and why.** Eighteen findings; fourteen answered in code, tests or these records. Left as they are:
  - **A launch can lose its one retry** (finding 7): the rule Jenna set is the launch refresh and nowhere else, so a later refresh doesn't owe one. Said above.
  - **The three tries start again if the Studio drops a blyg and lists it again** (finding 8), and the 2,000-entry limit on reading a Studio's list: both as they were before this rule. Said above.
  - **Bookkeeping that grows with the pending list** (finding 11): each try looks through the pending and seen lists on the main actor. With a thousand unreachable blygs that would be about a million comparisons spread over a thousand network waits; no real list is near that.
  - **Work on the main actor that grows with the library** (finding 12): an empty feed looks for the first saved post on each redraw (it stops at the first it finds); a blyg's page counts its posts on each redraw, as Your blygs already does (left for later, above); and the feed sorts every post inside the 14 days before keeping 200. All are a comparison or two per item, not a pass over each post's HTML.
  - **No test** for one fix: a blyg's "All posts" page drops a build that was cancelled, so an old one can't land on a newer one. It's a line in a SwiftUI `.task`, out of the unit tests' reach.
  - **A second round, on those fixes alone:** ten findings (three high, five medium, two on the tests), all in the retry rule's bookkeeping and the first import, and all answered. They're in the retry rule above: the count kept for the launch, how addresses are spelled, what the first import remembers and when, unfollows noted while a list is worked through, and no refresh of a blyg followed already. Also, a refresh of one blyg alone that fails now moves the feed's window too. One claim in them wasn't accepted: that the first import wrote the file once per already-followed blyg. Those saves were asked for back to back and went out as one write; the entries are now remembered together anyway.
- **The posting token goes only to the blyg's own host, over https (2026-11-25).** The API URL a Studio advertises is used only when it's https on the host and port the token was just checked against (no port means 443); anything else gets `{origin}api`. The check runs at connect and again whenever a saved URL is read from the library file or the Keychain, so one saved by an earlier build can't be used. It doesn't compare paths. A blyg that isn't https can't be connected: connect refuses before any request, a saved connection to one is dropped on load (its token stays in the Keychain, unused, until the blyg is removed), and the Studio client itself sends nothing to a URL that isn't https. It can still be followed and read where iOS loads it at all: the app has no App Transport Security exception, so plain http works only for local addresses, and the connect message no longer promises reading. Redirects are held to the same rule: URLSession follows them by itself after the first URL is checked, so the posting transport refuses any redirect that isn't https on the host and port the request was first sent to, and the call fails with `redirect-refused` before anything goes to the new address. A redirect it does follow gets the token put back if URLSession's proposed request arrived without it. *Beat:* trusting the advertised URL as it came (a Studio's answer could send the token to another host); always building `{origin}api` (ignores what the blyg advertises).
- **Backups on GitHub and the sandbox VM (2026-11-23).** Every push goes to GitHub and to a bare repo on `blyg-sandbox` (`~/backups/`), Jenna's choice of her exe.dev account as the second home. The local-only files go to a separate private repo and the VM through a script, never to the public repo, since the plan names work accounts. *Beat:* a new VM for backups (one more machine), and Time Machine alone (not off-site).

- **v0.1 signs in with a pasted Client-access token** (it lasts 30 days, with no refresh). OAuth comes in v0.2, once it's confirmed that Studio accepts an iOS app's https redirect. *Beat:* building OAuth first and risking the demo on an unknown.
- **iPhone only, iOS 18.0 and later.** The minimum is the plan's choice: it lets testers with older iPhones install the app, and the APIs needed (SwiftUI, PhotosUI, AuthenticationServices) all exist on 18. Xcode defaulted to iOS 27.2 and iPhone plus iPad. *Beat:* iPad support, which would need its own layouts. Jenna can still ask for it.
- **Posting reuses Studio's owner API as Studio's own JS SDK does:**
  - create a draft, upload the photo attached to it, and add `![alt](media/…)` to the text (the upload alone doesn't put it in the post), then publish;
  - each step sends the revision the previous one returned.

  Tried on the sandbox with the SDK first (2026-11-20). *Beat:* uploading the photo first. The upload must be attached to an item to be kept.
- **The Share extension reads connections straight from the shared Keychain.** Each token item also holds its blyg's title and API URL, so there's no App Group and no shared files. *Beat:* an App Group holding the library, which would need an explicit App ID and a capability.
- **Apple frameworks only;** no OpenAPI code generator, since it's a package. *Beat:* `swift-openapi-generator`.
- **Support and privacy pages on GitHub Pages from `docs/`**, not on the VM. They're versioned with the code and need no server; the VM keeps the sandbox blyg and, later, the OAuth files. *Beat:* the plan's pages on the VM.
- **Two looks, one layout: Studio (default) and System**, chosen in Your blygs → Appearance (2026-11-20).
  - Studio follows Blygger Studio's own stylesheet: Iowan Old Style for prose, a small sans "apparatus" for metadata, pencil blue (`#23608C`, dark `#8CC0E4`) for editorial marks, hairlines instead of cards.
  - System is San Francisco and iOS colors, for people who prefer sans on a phone.
  - Only type and color change, so each feature is built once. *Beat:* keeping the original stock-list screens as a second layout, which would mean building every feature twice.
  - The setting lives in UserDefaults (privacy manifest reason CA92.1). The share sheet stays System, since sharing the setting would need an App Group.
  - Jenna saw a mockup of Studio-native first (claude.ai design canvas); she doesn't love the look but chose to match Blygger's design language.
- **Blyg stays minimal; Studio is the full editor (2026-11-22).** Studio already ships as an installable web app (`{blyg}/studio/manifest.webmanifest`, with a phone composer). So Blyg covers reading, quick posts, replies and the share sheet, and links to Studio ("Edit in Studio") for editing, threads with quotes, pins and withdrawal. *Beat:* reimplementing Studio's editor natively, or a second "maximal" app.
- **No link previews or embeds in Blyg for now.** Studio adds none to post HTML; its YouTube poster is a script on its own pages only. A post that links to another blyg post could show a quote card from the protocol (v0.2). *Beat:* fetching third-party previews, which would break "talks only to blygs and their media".
- **Third-party network services:** none of our own. The app fetches the blygs the user adds, plus any images or media their posts link to, which can be on other hosts. *Beat:* blocking images from other hosts with a content rule list, which keeps the privacy claim but leaves many posts imageless. The README says this plainly.
- **Sync from `items/index.json` and item documents, not `feed.xml`.** The spec makes item documents the ground truth and the feed a lossy signal. It also lists each version of an item separately, and must be rolled up by `blyg:id`. The feed is used only to find a manifest. *Beat:* the plan's "read `feed.xml`".
- **Never vary behavior by `generator` or `level`.** Spec §3.2 and §13.1 rule 8 forbid it. Posting will be offered when a blyg's `/api` answers and a token is saved. *Beat:* the plan's "read `generator` and only show Post when `/api` responds".
- **Identity is the URL the manifest was fetched from, after redirects (§12.2).** It is never taken from the manifest's `site` field. URLs with stray whitespace are trimmed for display and fetching, because live blygs published them; blyg.jdbb.net did until 2026-11-20.
- **Test data is a made-up blyg (`sample.example`), not copies of real posts.** ios.md says tests never name real people. Also, a copy in a public repo would outlive any post its author later withdrew. *Beat:* the plan's "saved copies of Jenna's public feed".
- **Post HTML renders in a `WKWebView` with JavaScript, frames and stored cookies off.** A link opens outside the app. The text follows Dynamic Type and dark mode through CSS. *Beat:* converting HTML to an attributed string, which uses WebKit anyway and is slow.
- **The timeline is ordered by each post's claimed `updated` date, capped at when the app first saw that version** (§13.7), so a future-dated post can't stay on top. *Beat:* trusting the claimed date.


- **Quote cards fetch only what a link proves is a blyg post (2026-11-22).** Jenna approved the privacy-page change first.

  - **What a card shows:** escaped plain text, never the linked post's HTML or images.
  - **Where:** on the post page only, never in the timeline.
  - **What's skipped:** links inside baked quotes (they're the quoted author's), the post itself, and the post it replies to.

Still unknown: whether Studio will redirect back into an iOS app. The costs: an Associated Domains file on a domain we control, signing changes, every tester's Studio being new enough, and the app and the share sheet racing to renew one token. ## Lessons

- **Write the note in the same step as the change it's about.** A blyg a Studio follows was added to the library and saved, and only marked as dealt with once its posts had been fetched. Unfollowed in that gap, with the app then closed, it looked new at the next launch and came back.
- **When two waiters share one answer, write the result down before either hears it.** Two Studios' lists asked after the same dead address and shared one request; each then recorded the failure in whichever order they woke, and one order counted the try twice. The request's own task now records it, once, before it returns.
- **Fixture posts have fixed dates, so anything measured from "now" needs a clock the tests can set.** The feed's 14-day window would have dropped the fixture blyg's oldest post, and failed the UI test, three days after it was written. The window takes `now` as a parameter; tests and the fixture app pass the fixture blyg's own date.
- **A plain `async` function doesn't leave the main actor.** With `SWIFT_APPROACHABLE_CONCURRENCY`, a `nonisolated` async function runs on its caller's actor, so `Syncer.refresh` decoded on the main actor whenever the model called it. Only `@concurrent` moves it. A fake that notes `Thread.isMainThread` when it's called shows which is happening.
- **Setting an `@Observable` property that's Equatable compares old and new first.** For the timeline that's a pass over every row on the main actor. So the timeline has storage of its own with `access` and `withMutation` called by hand, the comparison happens where the rows are built, and an unchanged timeline isn't set. From Codex's reading of the generated setter, not measured.
- **"Only X is still refreshing" is also true when X starts first.** Tests that stop a refresh half-way wait for the held request and for every other blyg's answer.
- **A test double that blocks a thread can stall every test.** Swift's pool has about as many threads as cores, and tests run side by side. Four fetches blocked on semaphores in one test left no thread for anything else until they timed out. Block a thread only where the test asks whether the main actor is free; to put steps in order, wait on a continuation.
- **Work marked as covered when a job starts isn't covered until the job succeeds.** The save loop cleared its list of refreshes waiting to be saved as it took its copy of the library; when that write failed, they had lost their own save. Hand the list back on failure. Codex found it on the fourth pass, in a fix made for its third.
- **`URL.path()` is percent-encoded.** `FileManager.fileExists(atPath: url.path())` is false for anything under `Application Support`, so the saved library was always read from its backup. Use `path(percentEncoded: false)`, and give test folders a space in their name. Found by the offline-state screenshot, not by the tests.
- **Default to the safest target, and make the target visible.** A composer that silently picks a blyg will eventually post somewhere unintended; this happened on the first try (build 6). A reply's natural home is the blyg it answers.
- **Two `@AppStorage` properties on the same key misbehaved.** The Settings screen and the root view both read `appearance`. After the first change, Settings stopped redrawing, so further taps looked dead; the value was still being saved. Fix: one reader (`ThemedRoot`) passes the theme down; Settings only writes. Caught by Jenna on build 3; a UI test now switches back and forth.
- **A web view's text reaches the accessibility tree late on a busy simulator.** The UI test waits 20 s for it.
- **A development archive doesn't register the bundle IDs.** With no capabilities that need one, automatic signing uses the team's wildcard profile, so App Store Connect's New App form can't find the IDs. An App Store export (`xcodebuild -exportArchive` with `destination` `export`, nothing uploaded) registers them. Afterwards, reload App Store Connect.
- **Internal TestFlight needs an emailed invitation, even for the account holder.** The tester shows as "Invited", and the app doesn't appear in TestFlight until the email's link or redeem code is used; refreshing TestFlight doesn't help. The external public link has no such step.
- **Check markdown on Studio's own renderer, not from memory.** On the sandbox, `npx tsx` with a script that imports `~/blygger-studio/src/markdown.ts` renders exactly what a post will show, math plugin included.
- **SF Symbols and Apple's system fonts can't be used in app icons** (license). The icon is drawn as shapes by `scripts/make-icon.swift`.
